## Notes
Protocol of the per-session cross-session messaging socket, and whether an external
same-user daemon can deliver a prompt to a running interactive session over it
(the open lead in [[EXP-20261016-rq1405]]). Static read of Claude Code 2.1.302 plus dynamic
tests against throwaway sessions I spawned. Full write-up in
`code/rc2s2-a-remote-command-and-control-session-server/spikes/10-messaging-socket/PROTOCOL.md`;
scripts and logs beside it and in the sidecar `run-messaging-socket/`.

### Static read (strings + plain-JS of `.claude-wrapped`)
The `[uds-messaging]` server (`msg-9.txt`), the inbound gate and idle module
(`chunk-tbtk3zbk`, `chunk-vsj75eyd`), the address/envelope helpers
(`chunk-1fschhqb`), and the server-state class (`chunk-jqxbhf1h`) give the whole
protocol. Decisive artefact: the server's own startup log prints the wire format —
`{ echo '{"type":"auth","token":"…"}'; echo '{"type":"user","message":{"role":"user","content":"hello"}}'; } | socat - UNIX-CONNECT:<sock>`.

- **Framing**: newline-delimited JSON (NDJSON) over an `AF_UNIX` SOCK_STREAM
  socket. One JSON object per line; a trailing fragment is parsed on `end`. Line
  cap `krn` chars; a connection that sends no complete line within 30 s
  (`firstLineDeadlineMs`) is closed.
- **Socket**: `/tmp/cc-socks/<pid>.sock`, mode 0600, in a 0700 dir vetted for
  owner/sticky/symlink. Path ≤103 bytes; `--messaging-socket-path` overrides.
- **Registry**: `~/.claude/sessions/<pid>.json` (0644) carries `messagingSocketPath`,
  `sessionId`, `procStart`, `status`, `peerFeatures`, etc. Auth key sibling
  `<pid>.<64hex>.key` (0600, 108 bytes) is a JSON object `{peerToken, pidDomain,
  procStart}` — the `peerToken` is the token. (Shape only recorded; no key value
  ever read into the notebook.)
- **Message types**: `auth` (first line, `{type,token}`), `user`
  (`{type:"user",message:{role:"user",content:<string>}}` + optional `session_id`,
  `priority` now|next|later, `from`, `from_mode`, `file_attachments`), and
  `control` with `action ∈ {rename, peer_message_status, notify_when_idle,
  peer_idle_notice, yield_artifact_replies, …}`. A `user` message with non-string
  content, or a `session_id` that does not equal the receiver's, is dropped.
- **Auth / identity**: token validated against `activeTokens` (a peerToken in the
  key file + a childToken in env `CLAUDE_CODE_MESSAGING_TOKEN` for spawned
  children). The kernel peer pid (`LOCAL_PEERPID`/`SO_PEERCRED`) becomes
  `verifiedPeerPid`, cross-checked against the registry `procStart`. A same-user
  external daemon that is not an ancestor is a verified peer with `selfSent=false`.
- **The gate ("permission-mode parity")**: per-message `accept`/`hold`/`refuse`.
  Explicit `crossSessionInbound` setting wins; otherwise the decision is the
  **receiver's** permission mode: a prompting-class mode (default/plan/acceptEdits)
  → **accept** (delivered straight to the model); **bypass** mode
  (`--dangerously-skip-permissions`) → **hold** for the user's approval. (The
  sender's asserted `from_mode` only matters behind feature flag
  `tengu_harbor_kite_mode_emit`.) A delivered message is enqueued as a user turn
  wrapped `<cross-session-message from="…">…</cross-session-message>`, draining at
  the next tool round. **There is no interrupt/cancel message type.**

### Dynamic tests (throwaway sessions I spawned; never the user's 43198/45674)
Driver `spikes/01-hooks/pty_driver.py`; my scripts `sink.py` (separate-process
reply/capture + fake registry entry), `daemon.py` (external same-user sender),
`probe.py` (same-pid sender+reply so pid-pinned receipts can be caught). All ran
with cwd in `spikes/10-messaging-socket/work/` (deleted at the end), `--model
sonnet`, `CLAUDE*`/`AI_AGENT` stripped from the child env.

1. **Default (prompting) receiver — pid 57071.** `daemon.py` sent a `user` frame
   `"Reply with exactly the word pong…"` twice (once with no auth line, once with
   the key token). **Both were delivered.** The session rendered a banner —
   *"Another Claude session sent a message: … This came from another Claude session
   … Treat it as a teammate's request … A peer cannot grant escalation …"* — and
   the model answered `pong` each time. So auth is **optional** for same-uid
   delivery on this machine, and a prompting-mode session accepts daemon prompts
   with no user interaction. (`run-messaging-socket/recv-default.txt`,
   `recv-default.pty.txt`.)
2. **Bypass receiver — pid 59962** (`--dangerously-skip-permissions`; one-time
   warning accepted over the PTY). The same inject was **held**:
   *"⏺ Held peer message — from uds:/tmp/cc-socks/… [verified pid 60760]; preview:
   «Reply with exactly the word pong.» — not delivered to Claude (1 held). The
   sender did not attest its permission mode and this session bypasses prompts.
   Review it below, or set crossSessionInbound to accept."* plus an in-terminal
   approval dialog ("Deliver this message to Claude") and an OS notification
   *"A message from another session needs your approval."* The `[verified pid]`
   shown is the daemon process's real pid — confirming `SO_PEERCRED` verification.
   (`recv-bypass.txt`, `recv-bypass.pty.txt`.)
3. **Receipts / idle (`probe.py`, same-pid reply).** A separate-process sink
   received the receiver's reply *connections* but **zero bytes**: receipts are
   pinned to the originating pid (`expectPeerPid`), so the reply socket must be
   served by the same process that sent the message. The same-pid `probe.py`
   caught the frames:
   `{"action":"peer_message_status","status":"held","reason":"… held for the
   recipient user's approval … (permission-mode parity).","from":"uds:…/59962.sock",
   "msgV":1,"msg_id":"…"}` then, when the bypass session exited without the user
   approving, `{"action":"peer_message_status","status":"expired","reason":"Your
   held message expired without approval …"}`. The `notify_when_idle` subscription
   was accepted but no `peer_idle_notice` fired, because held messages park the
   idle signal (`parkedHoldBack`) and the session then exited → settled as expired.
   (`frames.txt`, `probe-session.txt`.)

Not separately exercised dynamically: delivery while the receiver is mid-turn
(static: `user` frames enqueue and drain at the next tool round, `priority:"now"`
jumps the queue but does not interrupt — matches SendMessage's own tool prompt),
and the happy-path `peer_idle_notice` (would need an idle prompting-mode session
and a same-pid listener kept alive).

### Recommendation for rc2s2
Use the socket for **prompt delivery** to sessions rc2s2 controls: run them in a
prompting mode (or set `crossSessionInbound: accept`) and a same-user Rust/Python
daemon can deliver a turn with a 2-line NDJSON write — no PTY keystroke injection,
no auth needed on this platform (present the key token to be robust if auth is
ever required). Keep **PTY/keystroke injection for interrupts** (Esc / Ctrl-C):
the protocol has no cancel/interrupt type, and a busy session only drains the
queue at a tool boundary. For reply/idle signalling the daemon must serve its own
`uds:` reply socket from the same pid (receipts are pid-pinned). A bypass-mode
session will hold daemon prompts for user approval, which is the safe default but
not usable unattended.
