and is passed through to Claude verbatim. There is no membership check against the options.

Same rig as [[RUN-20261017-e1d84z]] (`hook_server_ask.py`, `settings-ask-perm.json`, PTY driver,
`perm` mode); logs in `experiments/EXP-20261016-rq1404/run-freetext/`.

Prompt: one question, exact text `Pick a colour`, header `Colour`, `multiSelect: false`,
options Red/Green. The hook's `PermissionRequest` returned `updatedInput.answers =
{"Pick a colour": "Teal"}` — a **plain string that is not an option label**.

What Claude received: the value was accepted and stored verbatim. `PostToolUse`
`tool_response.answers` was `{"Pick a colour": "Teal"}`, and the `tool_result` in the
transcript read verbatim (note the wording differs from the all-options case — off-menu
answers get the cautious framing):

> The user answered: "Pick a colour"="Teal". Read the answers carefully — they may request clarification, changes, or that you not proceed — and follow what they actually say.

The assistant printed `Teal`. The terminal showed `User answered Claude's questions:
 · Pick a colour → Teal` and `Allowed by PermissionRequest hook`.

So there is no separate "Other" key or shape: a free-text answer is just a string value for
the question, exactly like a chosen label. The validator (`ue`) accepts any string for a
question (length-capped); it never checks the string against the option labels. The UI's own
`__other__` sentinel and text-input field are an interactive-entry detail only — the hook
never uses it; it just supplies the final string.
